# Prompt Forge（提示词工坊）

给 DSH 的输入框加一个 `✦ Prompt` 按钮：点开一个面板，把你的草稿按「提示词心法」改写成能直接执行的提示词，或者先列出你没考虑到的未知。**改写结果不会自动覆盖草稿**——它按段/按条列出来，你勾选要用的部分，再决定「替换草稿」还是「追加到末尾」。面板里还有第三个页签「设置」，温度、先问再答、规则文件都能在那里直接改，不用手编配置文件；模型不单设，永远跟随当前对话。

插件只在输入框里由你点按触发：它不向模型暴露任何工具，agent 不会替你调用它，也不会在你没要求时改你的草稿。

## 它做什么

1. 在输入框里写草稿，一句话也行。
2. 点工具行左侧的 `✦ Prompt`：输入框上方展开面板，三个页签——`改写提示词` / `未知清单` / `设置`。
3. 点 `生成改写`（或 `扫描未知`），等模型返回。
4. 结果按行列出：改写稿按小节分（`目标`、`背景与约束`、`验收标准`……），未知清单按问题分（数量跟任务大小走，一行一个问句）。每行有勾选框，默认全选。
5. 调整勾选 → 点 `替换草稿`（只把选中的部分写进输入框）或 `追加到末尾`（接在你原有文字后面）。点 `关闭` 收起面板，草稿保持不动。

面板只读你的草稿：不点「替换/追加」，输入框里的文字一个字符都不会变。

## 改写依据：提示词心法

规则写在 [`doctrine.md`](doctrine.md)，由它驱动改写模型。这套规则来自一份个人整理的 AI 使用手册——《AI 使用心法》，把「怎么让 AI 把活干好」归纳成十来个可以照着做的动作；方法论源头是 Anthropic 官方博客的三篇长文：**《找到你的未知》**（动手前先把「自己不知道什么」找出来）、**《删掉 80%》**（把上下文与要求压缩到真正决定结果的那 20%）、**《更有野心》**（别只要一个能跑的东西，把标准和野心一起抬上去）。

落到提示词改写上，就是下面这几条：

| 心法要点 | 在改写里的落地 |
| --- | --- |
| 判据代替禁令 | 把「不要啰嗦」「写好一点」换成可外部验证的验收标准：条数、字数、必须包含的结构、必须给出的证据 |
| 先找未知再动手 | 原文够长时改写稿开头单独一节，要求对方先提 3 个「内行必问、外行想不到」的问题，只问不答；一句话任务则压成一条验收标准。可用 `askFirst` 关掉，改为在「未知与待确认」里写出「我据此推断的前提」与「仍需要你确认的点」 |
| 关键处留白 | 口味、价值取舍、风险偏好这类只有人能拍板的选择，写成「这一项由我决定，先给我选项」 |
| 便宜原型优先 | 大任务先要一个 10 分钟能看完的最小可运行版本，再迭代 |
| 抬一层野心 | 只「做完」不够，同一份交付里再给一个更高标准的版本，或一个被低估的更优解 |
| 上下文五层 | 身份 / 项目 / 能力 / 参考 / 即时；原文缺哪层就用「【待补：…】」占位，不编造 |
| 目标具体且难 | 把「优化一下」「处理一下」这类模糊动词换成可验收的结果描述 |
| 逆向面试 | 动手前先用三个问题面试委托人，把没想到的东西问出来 |

### 篇幅跟着任务复杂度走

改写**不套固定模板**：宿主先按草稿字数给这一份定预算，再让模型在这个预算里写；写超了自动复查、退回重写一次。

| 草稿字数 | 档位 | 改写上限 | 未知清单上限 |
| --- | --- | --- | --- |
| < 40 | 一句话任务 | ≤ 150 字 / 2 节（只写「目标」「验收标准」；「先问再答」压成一句话放进验收标准，不单独成节） | ≤ 2 条 / 70 字，每条 ≤ 28 字 |
| < 200 | 小任务 | ≤ 240 字 / 3 节 | ≤ 3 条 / 120 字，每条 ≤ 32 字 |
| < 800 | 普通任务 | ≤ 900 字 / 4 节 | ≤ 5 条 / 260 字，每条 ≤ 42 字 |
| ≥ 800 | 长任务 | ≤ 原文 × 1.4（不低于 1200 字）/ 5 节 | ≤ 6 条 / 420 字，每条 ≤ 60 字 |

结构按需要长：默认两节 `目标` / `验收标准（可外部验证）`；只有原文真的缺上下文、必须由人补，才加 `背景与待确认`；只有产出物的格式本身是硬约束，才加 `交付格式`。**不许为了对称把节凑满。**

未知清单同理：没有那么多真正的未知就少写几条，**一行只写一个问句**，不写「——为什么」这类解释（解释挤占的正是你最想看的那些问题）。

### 改写后的三条自查

返回之前宿主会用 `reviewRewrite` 过一遍，命中任一条就带着整改要求重写一次：

- **判据是不是禁令的反面**：「不要啰嗦」改成「每条 ≤ 30 字、最多 5 条」是合格改写；写成「要简洁、要清晰、要专业」等于没改——这类形容词判据会被抓出来，要求换成第三方能逐条核对的数量、条数或动作。
- **是不是有一节在复述目标**：如果「交付格式」只是把「目标」换个说法再讲一遍，算法判定重复，要求删掉那一节。
- **列点有没有编号、一条一行**：`验收标准` / `背景与待确认` / `交付格式` 里如果有多条要求，必须每行一条、以 `1. ` `2. ` 开头。判定看两件事：多行时至少两条带编号；只有一行时里面不能出现 `；`（那说明几条被压成了一段）。这一条直接关系到面板的勾选粒度——段落型的判据只能整节全选或全不选。

只输出提示词正文——不带前言、不带代码围栏（宿主还会再兜底剥一次围栏和「改写后：」这类前缀）。

未知清单也有自己的复查（`reviewUnknowns`）：条数超预算、单条太长、出现「——为什么」的解释，都会被指出来并退回重写一次。

### 改规则（不用改代码）

`doctrine.md` 每次请求都会重新读，改完存盘立刻生效：

- 直接改仓库里的 `doctrine.md`，fork / PR 都行；
- 或者把规则放进团队自己的规范仓库，在设置里把 `doctrinePath` 指过去（绝对路径，或相对插件目录的路径）。

`index.js` 里的 `BUILTIN_DOCTRINE` 是文件缺失时的兜底副本；`node --test` 会校验它和 `doctrine.md` 逐字一致——改完规则文件记得同步一下兜底。

## 安装

需要一个已安装 DSH、带 Web GUI 的 profile。

```bash
# 1) 先装本包的依赖：Config 的字段 schema 依赖 @deepseek-ai/schemastery
pnpm install
```

```text
# 2) 把本目录注册成 bundle
plugin_manager → action: install_bundle → target: <本目录的绝对路径>
```

装完在插件列表里应能看到 `dsh-prompt-forge`（`active`），**刷新一次页面**，输入框工具行左侧会出现 `✦ Prompt`。

> 以目录形式安装时 DSH 会把本目录链接进 profile：改完源码重新 `install_bundle` 即可生效，不需要重启应用。也可以先 `pnpm pack` 出 tgz 再装，适合只使用、不改代码的场景。

## 配置：面板里的「设置」页签

这个版本的 DSH 只有只读的插件列表，没有通用的「插件配置表单」页面，所以本插件把配置界面做进了自己的面板：`✦ Prompt` → 面板右上角 `设置`。

表单里的三项就是下面这张表。点 `保存` 之后：

1. 插件把自己的 Loader 条目改写成一条普通的配置覆盖（写进当前 profile 的 `cordis.patch.yml`，新增一行 `- id: prompt-forge / config: {...}`，下次启动也带着）；
2. 所有字段都声明为 `volatile`，所以在运行中的插件上**立即生效**——不用重启应用，也不用刷新页面；
3. 下次打开面板仍会读回当前值；点 `恢复默认` 直接把这写回默认值。

| 字段 | 类型 / 默认值 | 作用 |
| --- | --- | --- |
| `temperature` | number / `1` | 温度。越低越贴原文，越高越敢重组结构 |
| `askFirst` | boolean / `true` | 「先问再答」开关。关掉后不再要求对方先提问，改为在「未知与待确认」里写出「我据此推断的前提」与「仍需要你确认的点」各 1–3 条 |
| `doctrinePath` | string / `''` | 自定义规则文件。留空＝用插件自带的 `doctrine.md`；可填绝对路径或相对插件目录的路径 |

**模型没有设置项**：改写用的就是当前对话正在用的那个模型（宿主每次向 `agentDefaultModel.currentSelection()` 取），所以面板里那行「模型：跟随当前对话」是只读说明。这样插件不会和聊天用上不同的模型，也不会出现「设置里能改、但对话里改不了」的两套模型概念。

保存走的是宿主 `configEditor` 服务，和 DSH 自己写配置是同一条路径：文件锁、原子写、写完触发 reconcile。若 profile 的这条配置被 home patch 或命令行 overlay 覆盖，保存会失败并在面板里显示原因——那种情况下要去改覆盖它的那一层。

## 接口

三条路由（仅本插件的客户端调用，不注册为 agent 工具）。前两条的 body 都是 `{ "text": "..." }`，返回的 `parts` 就是面板里一行一条的数据（前端只负责勾选和拼接）：

```jsonc
// POST /promptforge/optimize  → 按小节切开
{ "ok": true, "value": {
  "text": "…完整改写稿…",
  "parts": [ { "heading": null, "body": "先问再答：…" }, { "heading": "目标", "body": "…" } ],
  "provider": "deepseek-account", "model": "deepseek-flash" } }

// POST /promptforge/unknowns  → 按问题切开
{ "ok": true, "value": {
  "text": "1. …？\n\n2. …？",
  "parts": [ { "heading": null, "body": "1. …？" }, { "heading": null, "body": "2. …？" } ],
  "provider": "…", "model": "…" } }

// 设置：GET 读当前值，POST 写 { "config": { ... } }
{ "ok": true, "value": {
  "values": { "temperature": 1, "askFirst": true, "doctrinePath": "" },
  "defaults": { "temperature": 1, "askFirst": true, "doctrinePath": "" } } }

// 失败
{ "ok": false, "error": { "code": "empty-draft", "message": "the draft is empty" } }
```

限制：草稿 ≤ 20000 字符，请求体 ≤ 200 KB，单次调用 ≤ 120 秒；生成路由只接受 `POST`，设置路由只接受 `GET` / `POST`，其余返回 405。设置写不进去时返回 `500 save-failed`（附宿主原因），宿主没有 `configEditor` 时返回 `503 no-config-editor`。

## 为什么这样实现（而不是别的做法）

- **只做一个按钮，两个页签**：输入框工具行很窄，塞两个胶囊会挤掉别的插件；面板里放页签，功能不少，占地不变。
- **不暴露成 agent 工具**：它是给人在输入框里用的插件。把改写能力注册成模型可调用的工具，等于允许 agent 在你没要求时改你的提示词——改提示词该由人按下按钮。
- **改写结果不自动回填**：改写是一种重写，接不接、接哪几段该由人决定。所以结果按 `parts` 列成可勾选的行，`替换` / `追加` 是两个显式动作。
- **切段放在宿主做**：`splitSections` / `splitItems` 在 `index.js` 里，浏览器只渲染 `parts`。逻辑可被 `node --test` 覆盖，客户端保持薄。
- **面板放 `conversation.input.dock`**：官方声明为「composer 卡片上方的整宽条目」，是唯一有纵向空间放多行文本的槽位；胶囊按钮里塞不下 5 行问题。
- **两个槽位之间用模块级 store 通信**：按钮与面板是同一次 `apply()` 里注册的两个组件，没有共同父级可传 props，模块级 store + `useState` 订阅最省事，也不依赖未公开的 client service。
- **读写草稿用槽位标准注入的 `useInput` / `inputActions.setDraft`**：不碰编辑器内部实现。
- **样式只用官方主题 token**（`--dsw-alias-bg-layer-*`、`--dsw-alias-border-l1`、`--dsw-alias-brand-primary` 等 14 个之一），不写死颜色，浅色/深色主题都对。
- **不用 `host.call`**：那是未公开的 package-private RPC；改用宿主 `ctx.webServer.register` + 浏览器同源 `fetch`（文档相对路径 `promptforge/optimize`），跨版本更稳。
- **`conversation.input.left` 用自己的 id**：`kind: list`、`replaceRisk: none`，只会在旁边加一格，不会顶掉别的插件。
- **Config 用 `@deepseek-ai/schemastery`**：与 DSH 设置页同一套 schema 体系；字段声明 `.volatile()` 才能进表单，并且写值直接提交到运行中的插件引用（不重挂载插件行）。
- **配置界面做进面板，写值走宿主 `configEditor`**：这个版本的 DSH 没有通用插件配置表单，与其教用户手编 `cordis.patch.yml`，不如把表单放进面板；但写文件这件事不自己干——`configEditor` 自带文件锁、原子写、reconcile 与回滚，自己写 YAML 迟早和 Loader 打架。
- **模型不给设置项**：设置项一旦能改模型，插件就会和聊天用上不同的模型，用户还得自己记住两套「模型」概念。改写的合理默认就是「和这段对话用同一个」，所以每次生成都向 `agentDefaultModel.currentSelection()` 取，设置里只留一行只读说明。
- **没有「追加规则」字段**：想追加规则，直接往 `doctrine.md`（或 `doctrinePath` 指向的文件）里写就是同一个效果，而且能进版本库、能被 diff 审阅。两套入口只会让人猜「我的规则到底加在哪一层」。
- **空答案重试一次**：推理型模型偶尔把预算全花在 reasoning 上、正文为空；`streamOnce` 会翻倍 `maxTokens` 并去掉 `reasoningEffort` 再试一次，避免面板里出现空白。
- **规则外置成 `doctrine.md` 而不是写死在代码里**：改写标准属于团队知识，不属于代码；外置后改规则不用发版，也能被 diff 审阅。
- **篇幅预算按草稿字数分档、由宿主算**：一句话的任务不该产出五百字。预算是代码算出来的硬数字，作为第一次调用末尾的「这一次的篇幅预算」交给模型；模型手感不可靠，数字可靠。
- **未知清单也分档、也只给问句**：上一版的「3–5 条、每条带一句为什么」对一句话任务同样是过度输出（实测 241 字）。现在条数与单条字数由同一套分档给出，解释整段删掉——未知清单的价值在问题本身。
- **写超了自动退回重写一次**：`reviewRewrite` / `reviewUnknowns` 只认能机器判定的问题（节数、字数、条数、单条长度、形容词判据、重复节、列点未编号、解释），最多纠一次——再纠就是抽奖，不如把结果交给人勾选。
- **「一条一行」也写进规则并加机器检查**：面板的勾选粒度是「行」，一段用分号连起来的判据只能整段全选或全不选。所以规则里明文要求编号，`reviewRewrite` 再用 `isNumberedList` 验证：多行时至少两条带 `1. ` 编号；只有一行时若出现两个以上 `；`，判定为「多条压成一段」退回重写。写在规则里靠模型自觉，加检查才靠得住。
- **温度默认 `1`**：实测 0.35 / 0.8 / 1 之间字数和结构差异都在噪声范围（同一温度两轮波动常大于跨温度差异），真正稳定输出的是规则与复查；`1` 的好处是遇到含糊草稿更敢补判据，坏处是偶尔更爱压成段落——由上面那条检查兜住。

## 验证记录

- `node --test`：35 个用例全通过（两种「未知」段、规则文件加载与兜底、切段/切条、改写篇幅分档、未知条数分档、两份复查与纠正、列点编号检查、配置读写与校验、旧字段清理等）。
- 篇幅实测（同一台机器、同一默认模型，改前 vs 改后）：

  | 草稿 | 改前（v0.4，固定五节） | 改后（v0.5） |
  | --- | --- | --- |
  | 21 字：把会议记录整理成三条待办 | 530 字 / 5 节 | 144 字 / 2 节 |
  | 58 字：准备产品评审会议程 | — | 246 字 / 3 节 |
  | 182 字：周报流程半自动化 | 667 字 / 4 节 | 304 字 / 3 节 |
- `plugin_manager install_bundle` → `application: applied`、`enabled: true`、`warnings: []`。
- 插槽实测：`conversation.input.left` 有 `prompt-forge`（order 1100），`conversation.input.dock` 有 `prompt-forge-panel`（order 130），均 `active`。
- Config：`Config.listConfigs` 里该行 `status: "schema"`，三个字段都投影进设置表单（`temperature` 默认 `1`）。
- 端到端：`/promptforge/optimize` 返回带 `parts` 的分节改写；`/promptforge/unknowns` 返回带 `parts` 的问句列表；`/promptforge/config` 的 GET 读回三个字段、POST 写回后 profile 的 `cordis.patch.yml` 出现 `prompt-forge` 配置行，且立即生效（下一次生成即用新值）；旧版留下的 `model` / `extraRules` 键在下次保存时被清掉（`pickConfigKeys`）。
- 工具清单：`Tool.listTools` 里**没有** `prompt_forge_optimize`（v0.6 起不再暴露给模型）。

## 已知限制

- 改写是单次调用，没有流式打字效果；长文本只能等结果。
- 面板高度上限 `46vh`，很长的改写稿要在面板内滚动。
- 勾选粒度是「小节 / 条目」级，不能在行内局部取舍。
- 篇幅只是**软约束**：模型是概率输出，复查只纠一次，仍可能略超预算（尤其是小任务里既要有验收标准、又要保留「先问再答」时）；未知清单的条数同理，偶尔会多给一条。列点编号也一样：纠一次仍可能退化成段落，此时面板里该节仍可整节勾选。
- 页签之间各自保留上一次结果，切换不会重跑；改过草稿后需要重新生成。
- 设置只有面板这一个入口：DSH 的插件列表里没有通用配置表单，别处改配置只能手编 `cordis.patch.yml` 或调接口。
